# TrivaConnect Copilot — Current System Capabilities

> **Status legend:** `IMPLEMENTED` — verified working end-to-end in code (and, where noted, on the isolated deployment). `PARTIALLY IMPLEMENTED` — real code exists but the capability is incomplete or requires manual steps the name implies are automatic. `PLACEHOLDER` — code/UI exists but has no real backing behavior. `NOT IMPLEMENTED` — no code path exists. `UNKNOWN` — could not be verified.
>
> All evidence paths are relative to repository root `Triva-ISP-audit/` unless absolute. Backend code lives under `new-infra/backend/source/src/`. This document reflects the code as of the Phase 4 AnyPay-only commit (`03dc1fc`).

---

## 1. Actual Architecture (verified)

| Layer | Reality | Evidence |
|---|---|---|
| Backend | Node.js + Express + TypeScript, single process serving HTTP API + Socket.IO + background jobs | `new-infra/backend/source/src/index.ts` |
| Database | PostgreSQL 16 + Prisma ORM | `new-infra/backend/source/prisma/schema.prisma`, `docker-compose.yml` |
| Dashboard | React 18 + Vite + Zustand + Axios, merchant/admin SPA | `src/App.tsx`, `src/pages/` |
| Captive portal | Separate static SPA (no framework), nginx-served, proxies `/api` + `/socket.io` to backend | `new-infra/captive-portal/` |
| Realtime | Socket.IO rooms `mac:<mac>`, `tenant:<tenantId>`, `tenant_portal:<tenantId>` | `src/socket/index.ts` |
| Deployment | Docker Compose on Dokploy: `postgres`, `backend`, `portal`, optional `backup` profile, optional nginx (commented out) | `new-infra/docker-compose.yml` |
| Payments | AnyPay Tanzania only (Phase 4). Provider enum `{VOUCHER, ANYPAY}` | `schema.prisma` `PaymentProvider` |
| Device model | Three disjoint device tables: `Router` (MikroTik), `TpLinkRouter` (OpenWrt), `OmadaSite` (controller-side record) | `schema.prisma` |

**Critical modeling fact:** there are **no `Customer`, `Site`, `Installer`, `Installation`, or `AuditLog` models**. The `Tenant` row IS the WiFi business/customer account. A "site" is implied only by individual device rows (`Router.location`, `OmadaSite.location`, `TpLinkRouter.location`). Grouping multiple devices into one physical site is not modeled. Roles are exactly `SUPER_ADMIN` and `MERCHANT` (`schema.prisma` `UserRole`).

## 3. Current Onboarding / Provisioning Flow (what actually happens today)

**MikroTik site today:**

1. SUPER_ADMIN (or signup) creates `Tenant` + user login.
2. Tenant pays subscription via platform AnyPay → `Subscription` ACTIVE.
3. Merchant opens dashboard → Routers → "Add Router", enters name + optional serial/MAC + hotspotName + location.
4. Backend creates `Router` row (control-plane IP, API creds, provisioningKey).
5. Merchant opens router detail → downloads **Auto Installer** `.rsc` or copies manual commands.
6. **Manual step:** installer connects to the router (Winbox/WebFig/CLI), ensures a hotspot server exists, imports the script. The script:
   - Fetches portal pages into the hotspot directory,
   - Adds walled-garden entries,
   - Installs a 15s scheduler that runs the sync script,
   - Registers heartbeat.
7. Router calls `/bootstrap/router/:key?serialNumber=..&macAddress=..` → backend binds identity, marks ONLINE.
8. Customers hit portal → pick plan → AnyPay push to phone → webhook → session ACTIVE (direct API or 15s pull-sync).

**Omada site today:**

1. Merchant creates `OmadaSite` (name, controllerUrl, controllerIp, ssidName).
2. Backend generates `radiusSecret`, upserts FreeRADIUS `nas` row.
3. **Manual step:** operator downloads portal page package, uploads to Omada controller, configures external portal URL + RADIUS profile + SSID in the controller UI.
4. **Manual step:** operator clicks "mark provisioned" (`POST /omada-sites/:id/provision`).
5. Client joins SSID → redirected to Triva portal → pays/redeems voucher → backend issues `OmadaPortalToken` → controller exchanges it for RADIUS credentials → client authorized.

Everything step-marked **manual** is where the current system ends and the Copilot's value begins.

## 4. UI Claims vs. Reality

| UI/name implies | Reality |
|---|---|
| "Auto Installer" / "zero-touch" | Generates a valid `.rsc` file. Human still creates hotspot server, transfers file, imports it. No discovery, no confirmation loop until the router calls home |
| Omada site "provisioned" | A button that flips `provisionedAt`. Actual controller configuration happened entirely outside the system |
| `RouterStatus ONLINE` | Means "router called us", not "site is healthy" (no WAN/user-traffic verification) |
| `dataLimitMb` on plans | Stored, but no enforcement code found — session limits are time/bandwidth only |
| `bytesIn/bytesOut` | Columns exist; never populated |

## 5. Existing Failure & Recovery Behavior

| Failure | Current behavior |
|---|---|
| Router behind NAT/unreachable | Pull-sync fallback — session stays PENDING ≤15s until router fetches it. Verified live |
| AnyPay down at initiation | 502 + payment FAILED (fixed in Phase 4) |
| Webhook arrives, tenant AnyPay misconfigured | 200-ack, payment remains pending for reconciler (Phase 4 fix) |
| Forged webhook body | Amount/currency ignored; authoritative check via provider status API |
| Bootstrap serial/MAC mismatch | 409 conflict (deterministic identity guard) |
| Subscription expired | `validateTenantAccess` → 402; router sync script → 404 "subscription inactive" |
| Omada token replay | 401 (single-use conditional update) |
| DB pool killed (Postgres restart) | `/health/db` → 503 so supervisor restarts process |
| Session expiry | Best-effort direct removal; reconciliation via next pull-sync |

**Not present:** staged rollback of partial configuration, installation state machine, retryable step records, installer-facing diagnostics beyond router ping.
